# Agentic CRM on Dify: Local-First Design

A privacy-first deployment of Dify on Windows with Docker Desktop, with a human-in-the-loop (HITL) approval gate in front of every CRM write. Local models do the reasoning. Only the final CRM write leaves your machine.

Status legend used below: **[stock]** works with stock Dify, **[config]** needs configuration only, **[build]** needs code changes in this repo.

## 1. Architecture

```
 [ Approver: Dify web app form ]  <---->  [ Dify (Docker Compose) ]
                                             api / worker / web / plugin_daemon
                                             db_postgres / redis / pgvector
                                             ssrf_proxy (all outbound HTTP/MCP)
                                                  |
        +-----------------------+-----------------+-----------------------+
        |                       |                                         |
 [ Ollama on Windows host ]  [ MCP gateway (HTTP/SSE) ]        [ CRM layer ]
   host.docker.internal:11434  local files, Python utilities     HTTP Request node,
   chat model + embeddings     ./volumes/mcp-shared              or n8n (optional)
```

- **Dify** runs the node graph, the HITL pause and resume, RAG over pgvector, and the logs.
- **Ollama** runs on the Windows host (not in a container) so it can use your GPU directly.
- **MCP** reaches Dify only as a remote HTTP or SSE server (see 3.3).
- **n8n** is optional and only worth adding when OAuth or retry glue becomes painful (see section 6).

Docker Desktop on Windows uses the WSL2 backend by default (Hyper-V is the alternative). You don't manage WSL yourself, but bind mounts from `C:` or `D:` go through its file sharing layer. This is fine for CSV drops. Keep databases on Docker named volumes, which the provided compose files do.

Steps (PowerShell, from `docker/`; the full step-by-step with checks is in `setupRunbook.md`):

```powershell
.\crm-local\bootstrap.ps1                  # creates/updates .env, generates secrets, layers the CRM compose file
.\crm-local\start-llama.ps1 -LlamaServer <exe> -ChatModel <gguf> -EmbedModel <gguf>   # local models
docker compose up -d                       # Dify + pgvector
docker compose --profile mail up -d        # optional: Mailpit for testing email delivery
docker compose --profile n8n up -d         # optional: n8n bridge
```

Open `http://localhost`, create the admin account, then continue below. `SECRET_KEY` is empty in `.env.example` and must be set before first start. DB and Redis passwords default to `difyai123456`; those services aren't published to the host, but change them on a shared machine (each is referenced in more than one place).

### Reproducible images **[config]**

`docker/crm-local/docker-compose.crm.yaml` pins every image to `tag@digest` (digests resolved from Docker Hub on 2026-10-17), so a rebuild pulls identical bits. Notable changes from the stock file: nginx `latest` to `1.30.6`, squid `latest` to `6.13-25.04_beta`, busybox to `1.38.0`, n8n `2.43.7`, Mailpit `v1.21`. The Dify images keep their versions (`1.17.1`, plugin daemon `0.6.10-local`, sandbox `0.2.15`) but are locked by digest.

Because this layer wins over `docker-compose.yaml`, **a Dify upgrade must update the tags and digests here too**, or Compose keeps running the old images. List the resolved set with `docker compose config --images`.

### Storage on the D: drive

- Databases, vectors, Redis, plugin storage and uploads are bind mounts under `docker/volumes/`, so they live wherever the repo lives (D:).
- Docker Desktop keeps **images and named volumes** (n8n data, agent sandbox volumes) in a single WSL disk file, by default `C:\Users\<you>\AppData\Local\Docker\wsl\disk\docker_data.vhdx`. To move it: Docker Desktop, Settings, Resources, Advanced, **Disk image location**. This moves everything Docker holds, not only this project, and restarts Docker. Do it before the first `docker compose up -d`.

Repo rule: `docker/.env.example` stays minimal, and optional settings belong in `docker/envs/*.env.example`. That's why the CRM settings live in `crm-local.env.example` and are applied by `bootstrap.ps1`, not added to `.env.example`.

### Networking gotchas on Docker Desktop

1. **`localhost` inside a container is the container.** Use `host.docker.internal` to reach Ollama or anything else on the Windows host. Docker Desktop provides that name automatically.
2. **Ollama must listen beyond loopback.** Set the user environment variable `OLLAMA_HOST=0.0.0.0:11434`, then restart Ollama. Allow it through Windows Firewall for the Docker network if prompted.
3. **Dify's SSRF proxy blocks private destinations by default.** HTTP Request nodes, MCP calls and tools go through `ssrf_proxy`, which denies private and loopback addresses. The example env allowlists `host.docker.internal`, `n8n` and `mcp-gateway`. Without this you'll see timeouts or 403s that look like network bugs.
4. **Model-provider calls are different.** They go from the plugin daemon, not the SSRF proxy, so the Ollama provider only needs the host to be reachable.

## 3. Models and tools

### 3.1 Ollama models **[config]**

Install the Ollama plugin from Dify's plugin marketplace, then go to Settings, Model Providers, Ollama and add:

- a chat model, base URL `http://host.docker.internal:11434`. Pick one that supports **tool calling** if you'll use agent nodes. Plain LLM nodes don't need it.
- an embedding model such as `nomic-embed-text` with the same base URL, for knowledge bases.

The marketplace needs outbound internet for the plugin download once. For a fully offline install use a local `.difypkg`.

**Other local servers (llama-server, vLLM, LM Studio, LocalAI):** model providers are plugins, so you can mix them and choose a model per node. Anything with an OpenAI-compatible API works through the **OpenAI-API-compatible** plugin.

- **llama.cpp `llama-server`:** endpoint `http://host.docker.internal:8080/v1` (match your port), model name as launched, API key only if you set `--api-key`. Start it with `--host 0.0.0.0` so containers can reach it, and `--jinja` if you need tool calling.
- In the compatible provider, set capability toggles (function calling, vision, context size) by hand, since Dify can't detect them. Agent nodes need reliable tool calling.
- **Qwen3.5 is a reasoning model: run llama-server with `--reasoning off` for these workflows.** With thinking on, each call spent roughly 5,000 to 6,000 tokens reasoning and took 100+ seconds, and two of five test calls hit a 6,000-token limit before producing any answer. With thinking off, the same five calls finished in about 15 seconds total. `start-llama.ps1` already sets it. If you want deeper reasoning for a specific step, use a separate model entry, not the default.
- A knowledge base is tied to the embedding model it was indexed with, so changing it means re-indexing.
- Model calls go through the plugin daemon, so they don't touch the SSRF allowlist.

### 3.2 Knowledge base **[stock]**

Set `VECTOR_STORE=pgvector` (already in the env example). Pricing sheets and playbooks go into a Knowledge base using the local embedding model. The pgvector container is separate from the main metadata Postgres.

### 3.3 MCP **[config]**

Dify's MCP client connects to remote servers over HTTP or SSE. There is no stdio transport. A local stdio MCP server must therefore run behind an HTTP gateway (for example an `mcp-proxy` style wrapper) in a container on the Dify network. The override file contains a commented `mcp-gateway` template with `./volumes/mcp-shared` mounted. Register it under Tools, MCP with `http://mcp-gateway:8000/...`. Check the exact menu labels in your version; I haven't verified them.

The shared folder is only visible to MCP if it's mounted into the gateway container. It is not shared with Dify's own containers. To get files into a workflow, return their content through the MCP tool or use Dify's file inputs.

MCP tools return data. They don't run arbitrary Python inside Dify. For inline scripting use the Code node, which runs in the separate sandbox container.

## 4. The core workflow

Create a **Workflow** app (the Human Input node isn't available in chat-type apps).

```
Trigger (Webhook | Schedule | Start)
   -> Knowledge Retrieval
   -> LLM (draft reply / score lead)
   -> Human Input (review + edit)
        |-- Approve --> CRM write (HTTP Request / tool)  --> End
        |-- Reject  --> (log) --> End
        |-- timeout --> (notify, no write) --> End
```

1. **Trigger [stock].** A Start node for manual runs; webhook or schedule trigger nodes exist in this repo for event-driven runs.
2. **Knowledge Retrieval [stock].** Pulls playbook and pricing context.
3. **LLM [stock].** Output feeds the review form.
4. **Human Input [stock].**
   - Form fields can be pre-filled from upstream variables, so the draft appears editable.
   - Each action button (Approve, Reject, Edit) is its own output edge.
   - The node pauses the run. Its timeout is hours or days (default 36 hours), with a separate timeout edge. **Always wire the Reject and timeout edges**, or an unattended run just expires with no outcome.
   - Delivery is the web app form or email. For a purely local setup use the web app. `APP_WEB_URL` must be set correctly, because it forms the approver's link.
   - Email requires SMTP. Mailpit (optional profile) catches test emails at `http://localhost:8025`.
5. **CRM write [stock/config].** HTTP Request node.
   - Static bearer tokens often expire (Salesforce access tokens last about two hours). Add a refresh-token exchange step, or move the write to n8n.
   - Use your org's real instance URL, not a generic domain.
   - Make writes **idempotent** (upsert by external ID, or an idempotency key) so a re-run doesn't duplicate records.
   - Only the approved edge may reach this node.

Privacy note: reasoning, retrieval and drafts stay local. The CRM write, and any cloud CRM read, necessarily leave your machine.

## 6. Optional n8n bridge

Use it when you juggle several OAuth apps (HubSpot, Salesforce, Slack) or need robust retry and error handling.

```
CRM event -> n8n (fetch, clean) -> Dify workflow (draft + HITL)
                                        |
        n8n webhook  <-- final HTTP Request node at the end of the Dify workflow
        n8n -> writes to CRM with its native integrations
```

- **Into Dify:** either call `POST /v1/workflows/run` with an app API key, or post to a Dify **webhook trigger** node (no app key needed). From inside the compose network, n8n reaches the API at `http://api:5001`.
- **Back to n8n:** Dify has no built-in completion callback. End the workflow with an HTTP Request node that posts to the n8n webhook (`http://n8n:5678/webhook/...`). Make sure `n8n` is in the SSRF allowlist (it is in the example env).
- **Human wait:** a run can sit paused for hours. Don't hold an HTTP request open for that. Use async or streaming handling, and test how the API reports a paused run in your version before depending on it.

## 7. Roadmap

1. **Phase 1, stock Dify:** the section 4 workflow end to end with Ollama, pgvector, web-app approvals and an HTTP CRM write. Prove the loop.
2. **Phase 2:** CRM tool plugins (replace raw HTTP nodes), Slack delivery, richer review fields.
3. **Phase 3:** approval inbox with owner routing and audit.
4. **Phase 4:** canvas ergonomics (inline previews, partial re-run, batch view).

## 8. Open questions to settle early

- Which CRM first (Salesforce, HubSpot, other) and which objects are writable by the agent?
- Who approves, and is it one person or routed by record owner? This decides whether Phase 3 comes before Phase 2.
- Is a cloud CRM acceptable given the privacy goal, or does it need a self-hosted CRM?
- Which Ollama model fits your GPU and has reliable tool calling?

## 9. End-to-end automation around the call

Everything except the live call, as separate small workflows that share the CRM as state. Dify keeps no memory across runs, so each workflow reads the deal record, does one job and writes back, and a webhook or schedule starts the next. See `sales101.md` for the sales background.

```
Lead arrives -> Enrich + score -> Route -> First reply / outreach -> Nurture loop
   -> Meeting booked -> Pre-call brief -> [ LIVE CALL, human ]
   -> Transcript summary -> CRM update -> Follow-up draft
   -> Proposal / quote -> Negotiation support -> Close handoff
```

| # | Stage | What it does | Approval gate | State |
|---|---|---|---|---|
| 1 | Intake | Webhook from the form, dedupe against the CRM, create or update the contact (idempotent) | No | [stock] |
| 2 | Enrich + score | Enrichment API, LLM scores against the ICP and fills BANT as known / unknown / guess | No | [config]; enrichment API is yours to supply |
| 3 | Route | IF/ELSE on score, assign owner, notify | No | [stock]; owner-aware routing is [build] |
| 4 | First reply / outreach | Knowledge retrieval, draft, **Human Input**, send | Yes | [stock]: the Phase 1 workflow. Add a suppression-list check before drafting. |
| 5 | Nurture | Schedule finds silent leads, drafts a follow-up with new value, caps touches, stops on reply or opt-out | Yes | [stock] |
| 6 | Scheduling | Offer slots through a calendar tool | First send only | [config] |
| 7 | **Pre-call brief** | CRM history + notes -> BANT gaps, objective, 3 discovery questions | No (read-only) | [stock]: `agentic_crm_precall_brief.yml` |
| | *Live call* | *Human* | | |
| 8 | Transcript to CRM | Local speech-to-text, LLM extracts summary, BANT, objections, next steps | Yes: before/after diff | [build]: needs the diff review UI |
| 9 | Follow-up email | Recap with agreed next steps | Yes | [stock] |
| 10 | Proposal / quote | Assemble from templates; discount caps in code force manager approval; the LLM never sets a price | Yes | [build] for CPQ integration |
| 11 | Negotiation support | Summarize redlines, flag non-standard terms against policy, draft responses | Yes, always | [stock] |
| 12 | Close / handoff | Onboarding task, customer-success notice; a loss reason is required before marking lost | No | [config] |

Cross-cutting rules:

- **Stop conditions:** every loop (nurture, outbound) has a hard cap and an opt-out check.
- **Failures:** a failed CRM write or API call routes to a human, not a blind retry.
- **Audit:** log who approved what and the exact text sent ([build]).
- **Approval volume:** with this many gates, one reviewer using separate links won't scale. The approval inbox ([build], Phase 3) is the fix. Until then, batch the gates.
- **Privacy:** drafting, scoring and summaries run on the local model. Enrichment, email, calendar and the CRM are external.

Build order: pre-call brief (7), then transcript to CRM (8, 9), then intake through first reply (1 to 4), then nurture and outbound (5) last because of compliance and reputation risk.

To change steps or decide which ones need approval, see `customizingWorkflows.md`: it covers the stock-canvas approach (templates plus a how-to for adding, removing and gating steps).

A shot-by-shot plan for a walkthrough video is in `videoWalkthrough.md`.

## 10. Later option: the Agents feature (beta)

Not part of the first build. Dify has a separate **Agents** page (marked beta) and a matching **Agent** block in the workflow canvas, backed by the `dify-agent` service (the `agent_backend` container). An agent is assembled from layers: instructions (`prompt`), a model (`llm`), plugin `tools`, `knowledge` retrieval, session `history` that can be resumed, structured `output`, and an optional `shell` workspace. Unlike the fixed pipelines in this document, an agent chooses which tools to call and in what order.

What it could offer here:

- **Research and enrichment:** an Agent node in the pre-call brief that looks up an account with whatever tools it needs, instead of a single CRM lookup.
- **Structured results:** the `output` layer returns a fixed shape that downstream nodes can rely on.

Where to be careful:

- **Keep writes behind a gate.** An agent that picks its own actions should produce a proposal only. Any CRM write or customer message stays behind a Human Input node (see `customizingWorkflows.md`).
- **Model support is unverified.** Agents need a model that calls tools reliably. `qwen3.5-9b` through llama-server has not been tested for this, and the OpenAI-API-compatible provider's function-calling toggle is set by hand.
- **Shell workspaces** depend on the `local_sandbox` container, which crash-loops with the released 1.17.1 image against this checkout's compose file (the compose passes `--require-auth-token`, which that image does not know). It is currently stopped, and would need an image built from this checkout.
- **Beta:** behavior and UI may change.

Suggested experiment once the four imported workflows run: replace the CRM lookup in the pre-call brief with an Agent node, compare brief quality, latency and failure modes, and decide whether the added flexibility is worth the reduced predictability. Everything above is from reading the repo's docs and UI file names, not from running it.
